# 예약 전 파트너 상세 조회 (#173)

## 화면과 데이터

- 예약 STEP 6의 `상세 정보` 버튼은 예약을 선택하거나 결제하지 않는다.
- 예약 소유자에게만 해당 예약의 `ACCEPTED` 파트너 상세를 반환한다. 매칭이 끝나거나 파트너가 정지되면 조회할 수 없다.
- 실제 자기소개, 관리자 검증 근무 병원·기간·부서·업무, 인증된 자격 명칭·발급기관, 실제 평점 및 마스킹된 공개 후기 최근 10개를 사용한다.
- 상세 자기소개·경력·자격·사진은 파트너의 버전별 공개 동의를 확인한다. 기존 파트너는 기본 미동의이며 프로필 화면에서 동의하거나 철회할 수 있다.
- 연락처·이메일·주소·생년월일·계좌·증빙 원본을 상세 응답에 포함하지 않는다. 기존 수락 카드와 이미 공개된 후기의 표시 기준은 별도이다.
- 활동 지역·가능 시간·이동 보조 항목의 기존 로컬 목업은 고객 상세에 사용하지 않는다. 프로필 미리보기에서도 목업 지역·시간·선호 병원·경력 연수를 제외했다.

## 경력 등록과 검증

1. 파트너가 `/partner/profile`에서 실제 병원·기간·부서·업무를 등록한다(최대 20개).
2. 심사 담당자 또는 전체 관리자가 `/admin/qualifications?kind=work`에서 별도로 제출받은 경력 증빙을 확인한다. 이 PR에는 증빙 업로드 경로를 추가하지 않았다.
3. MFA 인증 후 검증 사유(5~500자)를 입력해 완료 처리한다. 사유는 접속기록과 파트너 알림에 기록하며 고객에게 노출하지 않는다. 사유에 계좌·환자 정보 등을 넣지 않는다.
4. 검증된 항목의 수정은 삭제 후 새로 등록·검증한다. 관리자는 검증을 심사 대기로 되돌릴 수 있다.
5. 공개 동의한 파트너의 검증 완료 경력만 예약자에게 표시한다.

파트너 계정 삭제(기존 탈퇴 흐름) 시 신규 공개 동의·경력 테이블은 FK cascade로 함께 파기된다.

## 배포 전 확인

- 마이그레이션 `20260708000063_partner_public_details.sql`을 대상 DB에 먼저 적용해야 한다. 기존 데이터에 임의 경력이나 공개 동의를 채우지 않는다.
- 이 PR은 `dev` 대상이다. 운영 DB 적용·main 병합·운영 배포는 별도 진행한다. #177의 61·62 마이그레이션과 대상 DB의 이력을 확인하고 적용 순서를 정한다.
- 개인정보처리방침에 파트너→예약자 공개 항목·대상·목적·기간 및 동의·철회 안내가 반영되었는지 운영 공개 전에 확인한다. 현재 방침 제5조의 고객→파트너 제공 조항은 이 공개의 근거로 사용하지 않는다.
- 경력 증빙을 전달받을 실제 운영 채널과 담당자를 확인한다. 증빙 확인 없이 검증 완료 처리하지 않는다.
- 사진 signed URL은 기존 유효기간 동안 접근될 수 있으며, 철회 전에 조회한 정보는 회수할 수 없다.

## 검증

`scripts/test-partner-details.sql`은 로컬 Supabase에서 트랜잭션 안에 테스트 데이터를 만들고 rollback한다. CI도 동일 테스트를 실행한다. 익명·타인 예약·미수락 파트너·자가 인증 차단, MFA 심사, 공개 동의·철회, 공개 필드 제한, 예약 상태 유지, 계정 삭제 파기를 검증한다.
