# 첫 1시간 무료 이벤트 (#159)

## 구현한 흐름

1. 고객 팝업은 DB의 `active && integration_ready && used_count < 20`일 때만 표시한다. 카카오톡 CTA는 기존 채널이며 분석은 기존 동의 게이트가 있는 `trackContact`만 사용한다.
2. X·ESC·배경 클릭으로 닫으면 로컬 날짜 기준 당일 재노출하지 않는다. 서버 상태를 주기적으로 다시 확인해 소진·비활성화를 반영한다. 관리자는 같은 HTML 팝업을 미리보기로 확인한다.
3. 인증된 고객만 자기 예약의 이벤트 자격을 조회한다. 실제 본인인증 제공자 확인이 기록된 별도 서버 전용 식별 테이블을 사용한다. 수정 가능한 프로필의 휴대폰/인증시각만으로 인정하지 않는다.
4. 이벤트 적용을 선택하면 포인트를 사용하지 않는다. 서버·DB가 상품별 첫 1시간(20,000원/25,000원), 신규 여부, 제외 여부와 정원을 다시 확인한다.
5. PG 요청 전에 임시 정원을 확보한다. 캠페인 행 잠금·계정 및 식별값의 부분 유일 인덱스가 중복/정원 초과를 막는다. 임시 확보는 확정 순번이 아니며 실패·만료 시 해제한다.
6. `finalize_payment` 안의 PAID 전이에서 확정 순번을 부여한다. 예약 확정이 실패하면 결제·순번도 같은 트랜잭션에서 롤백된다. 기존 승인 라우트가 PG 승인을 보상 취소한다.
7. 할인 전 총액·이벤트 할인·실제 청구액을 보존하고 회사 수수료에서 할인액을 부담한다. 파트너 선결제 기준 지급액은 유지한다. 이벤트 금액은 포인트 원장으로 복원하지 않는다.
8. 확정 후 취소·노쇼·탈퇴해도 USED 순번은 복원하지 않는다. 관리자는 전체/정산 duty 및 AAL2로 현황·예약번호 검색·페이지 이동·활성 상태 변경을 사용한다. 직접 테이블 열람/쓰기·식별값 노출·수동 재배정은 제공하지 않는다.

## 활성화 전 결정과 추가 연결이 필요한 항목

**초안 PR이며 고객 노출과 할인은 기본 비활성이다. 아래가 해결되기 전에 `integration_ready`를 바꾸지 않는다. 관리자 RPC도 준비되지 않은 캠페인의 활성화를 거절한다.**

- 실제 휴대폰 본인인증 업체와 서버 검증 콜백이 없다. 업체·인증 결과 검증 및 계정/휴대폰 기준의 안정적 HMAC 발급 방식을 확인해야 한다. 이메일 인증이나 클라이언트가 준 전화번호를 본인인증으로 대체하지 않는다.
- 본인인증 식별값/혜택 이력의 보유기간·동의 및 개인정보처리방침 반영이 필요하다. 캠페인 중 재가입 방지와 개인정보 파기 기준을 함께 확정해야 한다. 원문에 없는 무기한 보관을 승인된 정책으로 취급하지 않는다.
- 취소 시 기존 현금 환불 원장 흐름은 할인 후 수납액을 한도로 처리하지만, **노쇼/제공 불가/조기 종료의 이벤트 적용과 차감 정산 문안은 확인이 필요하다.** 특히 노쇼를 정상 제공한 무료 1시간과 같이 볼지 결정되지 않았다. 현재 일반 서비스 종료 코드를 그대로 활성화하면 노쇼 환불/파트너 차감 정산이 이벤트 조건과 어긋날 수 있으므로 실제 캠페인을 열지 않는다. 결정 후 고객 결제 상세와 최종 정산 경로까지 회귀 검증한다.
- 임시 확보 중 남은 인원은 보류될 수 있다. 사용 인원은 실제 확정 순서로만 증가한다. 단순 상담/클릭 순서로 배정하지 않는다. PG 진행 중 기한 경과로 승인이 취소되는 예외를 운영팀이 확인해야 한다.
- 실제 테스트 계정 제외 목록과 첫 이용 이력 기준을 운영팀이 확인하고 본인인증 연결에서 `excluded`를 설정해야 한다.

`legal-check`의 미확정 정책을 임의 확정하지 않는 지침에 따라 위 내용을 결정된 것으로 공개하지 않는다. 이 PR은 안전하게 꺼진 상태에서 구현을 리뷰하기 위한 것이다.

## 검증 및 적용

- SQL 테스트: 기본 비활성·서버 전용 확보·식별 데이터 접근 차단·MFA·준비 전 활성화 차단·예약 소유권·미인증/제외 계정·금액 위변조·포인트 중복·상품별 할인·주말 할증·멱등 재시도·실패 해제·20/21명 경계·확정 롤백·취소 미복원·소진 숨김.
- 로컬 동시성 테스트: 23개 동시 확보 요청에서 20개 성공/3개 거절을 확인하고 테스트 데이터를 정리한다. 원격 Supabase 주소에서는 실행되지 않는다.
- DB 마이그레이션 66은 스테이징 적용 전 다른 PR의 61~65 이력을 확인한다. 실제 원격 DB 적용·운영 할인·main 병합은 하지 않았다.
- 최종 결정과 본인인증 연동 후 별도 검증 PR에서 활성화 준비 상태를 완료한다. 이 초안만으로 고객 프로모션을 게시하지 않는다.
